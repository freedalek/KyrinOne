## 背景：严密的浏览器管控策略，存在一个关于「IP」的盲区

客户内部已完成严密的数据资产分级分类，并对终端数据外发通道做了细颗粒度管控。浏览器上传行为按数据密级划分管控强度，策略本意如下：

| 上传场景                                      | 策略预期                 | 当前实际表现         |
| --------------------------------------------- | ------------------------ | -------------------- |
| 中/高密级 · 非白名单站点（域名访问）          | 阻断上传                 | 终端 DLP 直接阻断    |
| 中/高密级 · 白名单站点（域名访问/IP访问）     | 记录上传行为             | 记录，不阻断         |
| 低密级（域名访问）                            | 记录事件（计划阻断上传） | 记录，暂时不阻断     |
| 通过 IP 地址访问站点（非白名单IP） · 任意密级 | 记录事件（计划阻断上传） | **仅记录，无法阻断** |

远期规划是「阻断所有发往非白名单网站的数据上传」。但当下存在一个无法回避的缺口：**DLP 的阻断动作只能对「域名访问」的网站生效**。一旦用户以 IP 地址直连网站，DLP 无法判断该IP指向的网站到底是什么，也无法判断它是不是业务所需，只能选择退而求其次，先记录事件，然后人工审计。

## 调查：一次例行审查，抓到一个漏网之鱼

> 终于开始讲正事了。。。

某天处理日常任务时，顺便在 DLP 事件记录里扫了一眼。按惯用的审查方法：先排除能确认没有风险的事件，再**把浏览器事件中通过 IP 访问的尽可能都筛出来**，然后忽略几个已经很熟悉的正常业务IP触发的事件（需要结合具体的url等信息，不能只看IP）。就在这个「排除」的过程中，一个非常不起眼的IP地址吸引了我。

```text
DLP 事件记录
├─ 1. 排除：确认没什么风险的事件
├─ 2. 筛选：通过浏览器上传文件的事件中通过 IP 访问网站的那一部分
├─ 3. 忽略：正常业务IP触发的事件（需要结合具体的url等信息，不能只看IP）
└─ 4. 命中：一个可疑的 IP 地址（需要依据经验以及url、数据内容等信息）
        └─ 访问确认 → 某学校云盘
```

顺着这条线查下去：

1. 访问该地址，确认是一所学校的云盘；
2. 核对客户内网，**不存在该地址**；
3. 无论从客户的内网还是外部公网访问这个IP，都会指向这个学校的云盘；
4. 到此已经能确认有用户向学校云盘上传了文件；（大部分终端DLP产品具有截图功能，在启用了这个功能的情况下，很大概率能直接从截图上看到用户上传文件的目标是哪里）
5. 筛选出全部去往该地址的事件，逐条查看上传的证据文件。

用户上传的文件一眼可辨——**是与生产、研发相关的数据**。而且，这些文件类型没有出现在数据资产的样本中，因此**分类和密级未被识别**。若审计时不够细心，这批上传很可能就此漏掉。

## 升级：从「批评教育」到安全部门介入

按以往的处理惯性，提交审查后会是常规结局：由甲方的同事联系当事人的上级经理核查确认，如果数据保密等级不高、能确认没有进一步泄漏、当事人不存在恶意泄漏或盗窃数据的行为，那么最终会确认数据被从云盘上删除后，批评当事人、再做一轮安全意识宣贯。

但是，这次有点不一样：

- 涉事员工是正式员工，还用以前学校的云盘这个行为就非常可疑了；
- 这位员工**同时参与客户公司与客户母公司的项目**；
- 其上级经理安全意识很强，当即联系安全部门领导说明情况并展开详细调查；
- 事件严重等级骤然超出预期。

最终，在多轮核实下确认数据并未进一步外泄，一直保存在云盘上，没有落到其他终端；涉事文件在上级经理的监督下从云盘删除。

## 根因：DLP 为什么拦不住「IP 访问」？

> 事后思考

根本原因在于 **IP 地址本身不可信**。对 DLP 而言，一个通过 IP 访问的站点，既可能是业务真实需求，也可能是用户自建的内网环境——只要终端能连到公司外部网络，或在内网中自建一个局域网，这种风险就无法避免（其余可能的绕过场景在此不展开）。

更棘手的是，**IP 段无法充当信任边界**：

| 网络环境            | 典型 IP 段  |
| ------------------- | ----------- |
| 企业内网            | 192.168.x.x |
| 手机热点 / 家庭宽带 | 192.168.x.x |
| 酒店、咖啡店 WiFi   | 192.168.x.x |

比如内网常见的 `192.168.x.x`，与手机热点、家庭宽带乃至酒店或咖啡店 WiFi 的网段**完全相同**。这意味着，只要基于「IP 位于内网段」做白名单判断，就等于把上述所有外部网络一并当成了「内网」。若事件不被记录，这个风险将完全不可见。

## 解决方案：

- **事件全记录 + 人工审计，仍是当下最有效的兜底**。在终端 DLP 负载与服务器存储可承受的范围内尽量留存全部事件，并配合一定力度的人工审计——做不到事中阻断，但能保证证据留存与及时发现。
- **IP 白名单能够缓解，但不能根治**。严格界定内网 IP 段、规范公网 IP 白名单申请，阻断向非白名单公网IP传输文件的行为，可以降低风险暴露面，但解决不了 IP 灵活性带来的根本问题。
- **截图能力无法替代审计，也未必能交给 AI**。多数终端 DLP 产品自带截图功能；此类场景常需截图辅助判断，因此该环节甚至难以接入 AI 自动分析。事件记录 + 人工审计依旧是主线。
